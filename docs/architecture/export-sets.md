# Export sets and native output jobs

MultiCAD stores reusable export definitions in the canonical document. Export uses those definitions to select current parts, occurrences and drawing pages, then asks an installed provider for an attributable preview. A Run rebuilds the accepted immutable source before writing files. Display meshes and previously retained viewport geometry do not participate.

## Saved definitions

The [`exchange.export_set` definition](../../crates/multicad-core/src/exchange/source.rs) uses the existing `ExportSet` entity and capability `exchange.export_set.1`. `prepare_set` prepares one guarded, undoable source edit. Recipe and page identities survive display-name changes and file reopen.

A scope is the whole project, one explicit assembly, or explicit Part and Instance IDs. An optional tag predicate intersects that scope using exact case-sensitive All, Any and Exclude tags. Occurrences use their source Part's tags. Visibility and current viewport selection never alter a saved scope. Selection can be captured explicitly when entering Export and copied into an explicit definition.

The [resolver](../../crates/multicad-core/src/exchange/resolve.rs) preserves Part and occurrence identities separately. A root Part and two placed copies are three distinct subjects. Missing roots fail resolution; an empty tag match remains empty. Current consumed producers are excluded by the native provider with a visible reason. First-level placed Parts are supported; nested assembly geometry remains unsupported.

Pages refer to stable drawing-book and nested page IDs. Explicit pages retain selection order. Recipes persist units, file/product names, hierarchy, manufacturing layers, mesh tolerances and removable-aid policy. Saving a setting does not assert provider support.

## Preview and Run

[`ExportStamp`](../../crates/multicad-core/src/exchange/resolve.rs) binds a result to document ID, Session revision and canonical source hash. `PreviewKey` also identifies the set and resolved output plan. A provider/build identity separates output generated by different implementations or geometry policies. Untagged builds use a process-specific identity.

The [native provider](../../crates/multicad-model/src/export/mod.rs) compiles an owned current `Model` on its worker thread. It selects exact local Part solids or exact world-space occurrence solids. It publishes plain metadata: matched identities, selected pages, recipe status, exclusions, filenames, world bounds, solid count and volume.

The native provider supports:

- separate STEP files in millimeters, with filename-only naming;
- removable FDM aids included or excluded by their aid feature, for STEP, planar DXF and mesh recipes;
- [explicit planar-face DXF](planar-dxf.md) with declared units and exact closed contours;
- [OBJ, 3MF and STL](#mesh-output) in millimeters, centimeters, meters or inches, as separate parts or one assembly file;
- [GLB scenes](#glb-scenes) in meters, for Blender and other scene tools.

- [multi-page PDF and per-page drawing DXF](drawing-exports.md) from checked drawing pages;
- [schedule CSV](#schedule-csv): one BOM, cut list or other schedule per recipe.

Export → Print builds a single [3MF print package](print-packaging.md) from chosen Parts and their removable aids, without a saved export set.

Other STEP units, STEP product-name attributes, preserved STEP assembly hierarchies, and GLB in units other than meters report Unsupported. Any Empty or Unsupported recipe blocks the whole Run. A preview never substitutes another scope or format.

## Mesh output

The [mesh writers](../../crates/multicad-model/src/export/mesh.rs) tessellate exact native solids at the recipe's chord and angular deviation. Viewport tessellation and display meshes are never inputs.

| Hierarchy | OBJ and STL | 3MF |
| --- | --- | --- |
| Separate parts | One file per Part or occurrence, in world coordinates | One file per Part or occurrence: one object and one identity build item |
| Preserve assembly | One file with every Part in world coordinates, since neither format has instancing | One file with one object per component definition (the producing feature) and one build item per occurrence, carrying its rigid pose |

- **Units.**
  - OBJ states its unit in a `# units:` header and scales coordinates.
  - STL is binary with outward facet normals. The format has no unit field, so coordinates use the chosen unit and the 80-byte header names it (`units=millimeter (not stored by STL)`). Readers that assume a unit may scale it wrongly.
  - 3MF declares `unit` on the model. Translations in 3MF build items use the same unit.
- **Names.** Product names use the Part and occurrence names; filename-only naming writes `object-N`.
- **Packaging.** 3MF packages contain `[Content_Types].xml`, `_rels/.rels` and `3D/3dmodel.model` as stored ZIP entries with a fixed timestamp, so identical source produces identical bytes.
- **Evidence.** Each artifact records objects, build items, triangles, chord deviation and the placed tessellated volume.
- **Readback.** Publication reads every OBJ, 3MF, STL and GLB back and requires:
  - the same bytes as generated, and the same objects, build items and triangles (STL keeps no objects, so only its triangles are compared);
  - a matching tessellated volume;
  - world bounds within twice the chord of the exact solid's bounds;
  - a volume within the chord allowance of the exact solid's volume, so an open or mis-oriented mesh fails.
  - STL and GLB store single-precision coordinates, so their bounds and volume comparisons allow for that precision.
- **Removable aids.** A recipe with `ExcludeRemovable` leaves out Parts produced by `fdm.aid` features and lists them in the recipe report's `excluded_aids`; see [FDM aids](fdm-aids.md). Names and tags never classify an aid.

### GLB scenes

GLB is glTF 2.0 binary, for handing a model to Blender or other scene tools.

- **Scale and axes.** glTF is defined in meters with +Y up. Geometry and translations are converted from millimeters, and one root node turns the Z-up model into the Y-up scene, so Blender's importer restores Z-up at true size. A GLB recipe in any other unit is Unsupported.
- **Hierarchy.** Each scope root assembly and each enclosing occurrence becomes a named group node with an identity transform. Every Part or occurrence is a leaf node named like other product names and carrying its rigid world pose, so a placement is applied exactly once.
- **Instances.** Occurrences of one component definition share one mesh in the definition's local frame. A Part placed directly in the project is written in world coordinates.
- **Appearance.** Each Part's effective appearance becomes a metallic-roughness material: its sRGB color as a linear base color, with alpha blending below full opacity.
- **Not included.** Textures, normals, cameras, lights and render settings are not written. Importers compute normals.

[`tools/blender/glb_import_report.py`](../../tools/blender/glb_import_report.py) imports a GLB in background Blender and reports objects, parents, world bounds, shared meshes and base colors. It is a developer check, not part of the application.

### Schedule CSV

A `ScheduleCsv` recipe names a `ScheduleSpec`: the BOM (with its aid and
purchased options), panel cut list, machining, member cut list, weld or bend
schedule.

- **Subject.** Each recipe writes one file for the whole project. The Part
  scope and pages do not apply. The `{part}` naming token is the schedule
  kind, for example `bom`.
- **Content.** The provider builds the schedule with `schedules::build` from
  the owned current model. The bytes are exactly `Schedule::csv`; see
  [schedules](schedules.md#csv).
- **Evidence.** The artifact's `schedule` evidence records:
  - the spec and title;
  - the revision;
  - the row and column counts;
  - the hash of the CSV bytes.

  The evidence is part of the plan hash, so a changed schedule makes an older
  preview stale.
- **Readback.** Publication and bundle reuse compare the written bytes and
  hash with the generated CSV. They also parse the file back and check its
  kind and revision comments, the header and one record per row with every
  column.
- **Failure.** A schedule that cannot be built makes the recipe Unsupported,
  with the reason.

The direct **Export → Common → Schedule CSV** command uses the same builder
through `ExportWorker::schedule`. It writes a single file chosen in the
native save dialog, and only when the rebuilt CSV hashes to the accepted
preview. See [schedules](schedules.md#access).

Drawing recipes refuse a page whose linked schedule table is stale; see
[drawing tables](schedules.md#drawing-tables).

Run receives an immutable document snapshot and the exact accepted key. It resolves and compiles again, checks the key, and writes only the requested snapshot. Later edits leave an older preview available for inspection but disable its Run action. An already accepted Run retains its original source and actor attribution even if the user edits or switches documents.

## Publication and job lifecycle

The [publisher](../../crates/multicad-model/src/export/publish.rs) requires an existing absolute output directory. It writes a temporary directory beneath that root, reads each STEP back through a fresh reader, and compares solid count, volume and world bounds against the current native solid. Planar DXF verifies its complete freshly generated bytes and record structure; independent import tests cover geometry and file interoperability. These checks do not establish general BRep equivalence.

Each file and the ownership manifest are flushed before the staging directory is renamed to a source- and provider-identified bundle. A persistent per-set lock file serializes cooperating publishers. The OS releases the lock on process exit. The lock file is deliberately retained to avoid replacing a locked inode.

A repeated identical Run reuses a bundle only after verifying its provider/source/plan, expected filenames, regular-file bounds, hashes and format-specific readback. Unknown files, symlinks, missing files and modified content fail without overwriting that bundle. The project source is unchanged by both successful and failed output jobs. Power-loss durability of the containing directory is not claimed.

The [worker](../../crates/multicad-model/src/export/worker.rs) accepts at most four outstanding jobs, including unread replies. Accepted Run intents remain FIFO and are never silently coalesced. Cancellation is checked between native calls and before publication; it cannot interrupt an individual OCCT call. A completed publication remains a success. Unexpected worker exit fails active and queued jobs and closes that worker permanently. Drop requests cancellation without blocking the UI thread.

The [Export workspace](../../crates/multicad-ui/src/exchange/mod.rs) polls jobs for every open document. Pending writes prevent window close until their outcome is acknowledged; read-only previews do not create an unsaved-document warning. Source drafts require Save or Discard before other editing commands. The composition root installs the [native adapter](../../crates/multicad-app/src/exchange.rs); UI code owns no native CAD handles.

## Verification and limits

[Core tests](../../crates/multicad-core/tests/export_sets.rs) cover dynamic tag changes, added parts, rename/reopen, missing scopes, page order, filename collisions and transaction guards. [Schedule output tests](../../crates/multicad-model/tests/schedule_outputs.rs) cover CSV recipes, stale schedule tables in drawing recipes and direct CSV writes. [Native integration tests](../../crates/multicad-model/tests/export_sets.rs) write and read STEP solids, check transformed occurrence bounds, consumed exclusions, repeated publication and failed/cancelled runs. Worker tests exercise overflow, FIFO order, cancellation and exit failure.

[Workspace tests](../../crates/multicad-ui/src/exchange/tests.rs) cover source-neutral drafts, stale/foreign replies and actual egui actions. [Application tests](../../crates/multicad-ui/src/application/export_tests.rs) cover file-dialog guards and pending writes across hidden tabs. The production adapter test exports a real solid through the workspace and verifies its STEP volume independently.

These automated checks do not establish interactive performance, physical macOS acceptance or Windows/Linux runtime behavior. Additional providers must consume current exact geometry or checked drawing vectors through their own contracts. External MCP transport and durable on-disk job history are separate work.
